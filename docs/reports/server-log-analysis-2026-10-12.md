## 已修复的服务端问题

### 删除恢复标记导致反复强制刷盘

日志第 21635 行开始报告 `forced memtable flush to bound durable tail file count`，
同类记录共 2,217 条，监控表的文件计数从 256 增至末尾的 4,633。

代码中 `durable_tail::clear` 有意保留 `.clear` 标记，防止恢复时复活旧数据。
原压力统计把这些无法通过刷盘回收的标记也算入阈值，导致新写入的小 memtable
不断被强制刷盘。日志没有磁盘目录清单，不能确认每个文件的类型，但代码路径可以独立复现。

修复后压力统计排除 `.clear`，仍统计 tail、delete/update sidecar 和 flush intent。
保留恢复标记和原始文件总数统计，不直接删除线上文件；此修复不负责回收历史标记。
回归测试模拟反复新增、删除后留下标记，验证新行不会被错误刷盘，恢复时只返回有效行。

### Bulk 校验晚于约束列访问

缺列的请求可能发生越界 panic；日志未显示该 panic，属于代码审查发现的关联缺陷。

修复后在任何约束处理前校验列数、类型、列名及 NULL 限制。

## 后续：CASE / DECIMAL 聚合失败已修复

`case_expressions_execute_in_projection_and_aggregates` 的根因在 DECIMAL 投影快速路径：
它对不支持的 CASE/函数表达式仍执行标量求值，并把所有结果视为 scale=0 的原始整数，
随后直接构造 Decimal 列，绕过已有的整数到 DECIMAL 的按 scale 转换。

例如 `MIN(CASE WHEN volume = 0 THEN 5000 ELSE low_px END)`，其中 `low_px` 为
DECIMAL(18,4)。整数 5000 应转换成原始值 50,000,000，却被写成 5,000（即 0.5000），
使 MIN 错误返回 5,000，而非正确的 102,000（10.2000）。

现在快速路径对无法推导小数位数的表达式返回“不支持”，交由普通投影路径完成类型转换。
新增断言覆盖 searched/simple CASE、THEN/ELSE 的非零整数、直接投影和 GROUP BY 聚合。
原失败项及两组聚合专项测试已通过。

日志中的 `is_st` 导入目标是 `t_online_stock`：末尾错误被业务程序记录为
`columnar bulk t_online_stock close: ... schema=INT8 payload=INT32`。

后续修复全量验证：`cargo test --workspace --no-fail-fast` 成功退出，1191 项通过、0 项失败、12 项忽略。
Clippy 完成（23 条警告），本次修改文件的 rustfmt 检查及 diff 空白检查通过。

## 继续审查：写入与恢复路径

另外复现并修复两处缺陷，均不代表已确认线上发生数据损坏：

1. **Bulk DECIMAL 小数位数不匹配会静默改变值。** 原实现只校验类型标签，
   未核对 scale。载荷 scale=2、原始整数 12345（123.45）写入 scale=4 的列后，
   会被解释为 1.2345。现在在写入前拒绝 scale 不匹配的请求；回归同时验证拒绝后
   行数仍为零、正确 scale 可以正常写入并读取。
2. **刷盘清理失败后误删恢复标记。** `archive_or_remove` 吞掉文件删除失败，
   `finish_flush_batch` 随后仍删除 flush intent。若旧 tail 留在磁盘，重启时可能
   再次恢复已经写入 segment 的行。现在清理函数返回错误，清理未完成时保留 intent；
   成功清理源文件后，先同步目录再移除 intent（沿用项目现有 best-effort 目录同步机制）。
   恢复路径清理旧代文件同样传播错误。回归用不可通过 remove_file 删除的目录模拟故障，
   验证错误被返回且恢复标记保留。

两项新测试在修复前均失败，修复后专项测试通过。

### DECIMAL 乘法达到 scale 上限时未同步缩放原始值

继续检查发现第三处缺陷：两个 DECIMAL(18,10) 相乘，原始乘积具有 20 位小数，
输出元数据把 scale 限制为 18，但原始整数没有除以 100。因此 0.1 × 0.1 被读成 1.0，
1.0 × 1.0 则因未缩放的原始值超过 i64 范围而返回 NULL。

修复在转换回 i64 前，根据实际小数位数与输出 scale 的差对乘积缩放。
回归覆盖正数、负数、NULL，以及 memtable 与刷盘后 segment 两种读取状态；
该测试在修复前失败，修复后两组聚合专项共 24 项通过。

本轮三处修复最终验证：`cargo test --workspace --no-fail-fast` 成功，1194 项通过、0 项失败、12 项忽略。
Clippy 完成（23 条警告），修改文件格式检查和 `git diff --check` 通过。

## 继续排查：慢处理、卡住与连接可用性

### 日志证据与边界

- 145 次表突变锁慢等待，最长 2,617,392 ms（43.6 分钟）；56 次索引重建被客户端断开取消。
- 这份日志未出现 `connection limit reached`、`accept failed`、`connection error` 等连接拒绝证据。

  语句超时默认关闭；未明确设置时，单靠队列超时不能限制已经进入执行阶段的等待。

### 本轮已复现并修复

1. **约束锁等待不响应取消，INSERT 过早进入不可取消阶段。**
   主键/唯一键约束使用分条互斥锁，原来的阻塞 `lock()` 不检查断连、KILL 或语句超时。
   INSERT 更在拿锁和扫描约束之前就进入 Committing，导致后续检查全部失效。
   现在约束锁轮询取消，INSERT 完成约束检查后才进入提交阶段；REPLACE、UPDATE、DELETE
   和列式 bulk 统一使用该锁入口。测试持有约束锁、启动 INSERT 后取消，确认无需等待
   持锁者释放就返回错误，且没有插入行。已进入提交阶段的操作仍保证不会被中途取消。
2. **普通请求池满时无法 KILL。**
   原 KILL 与业务查询争用同一个执行池。旧测试给 KILL 独立的普通限流器，掩盖了问题；
   改为两个连接共享饱和的限流器后，旧代码稳定超时。
   现在单条 KILL / SHOW PROCESSLIST 使用共享于服务端连接的两个独立管理槽位，
   仍走原来的执行、认证与管理员权限检查，多语句混合请求不走该通道。
   新增普通请求池满时 PROCESSLIST 可响应的测试。
3. **异常丢弃 Handler 后 bulk 会话计数泄漏。**
   断连清理可能因执行槽不足而跳过，或任务发生 panic；原 Drop 没有释放 bulk 计数。
   全局 bulk 模式因此可能持续开启，影响后续落盘和索引维护。
   Drop 现在只对仍持有 bulk 状态的会话释放一次计数；正常清理已经清除标志，不会重复释放。
   该兜底不冒险在 Drop 中执行强制刷盘。
4. **文档规定的 SHOW FULL PROCESSLIST 解析失败。**
   原解析器只接受 SHOW PROCESSLIST FULL。现在同时支持 SHOW FULL PROCESSLIST，
   保留旧形式兼容。管理请求分类测试覆盖注释、分号、无效语法和混合语句。

登录日志增加数据库名，bulk 错误日志增加数据库与会话 id，便于后续定位具体连接。
