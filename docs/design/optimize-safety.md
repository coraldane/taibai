# OPTIMIZE 的提交、读取与资源边界

适用于 `OPTIMIZE TABLE`、`OPTIMIZE TABLE ... ON PARTITION` 及共用 Compactor 的后台整理。

## 段发布与读取快照

段发现与替换发布共用短期目录互斥锁。查询在发现段前取得读者租约；流式游标和后台解码线程将租约保持到各自读取结束。非流式扫描和元数据聚合通过 `with_table_flush_read_lock` 同时持有租约。

替换先写并同步 `.replace` 日志，再发布新段。发布后日志提升为不依赖新段继续存在的 `.retire` 日志。段发现排除日志中已退休的路径，因此旧文件因读者仍在使用或 Windows 删除共享限制而保留时，新查询也不会重复读取。

读者租约释放后回收旧文件；物理删除在目录锁外执行。删除失败保留日志，由启动恢复重试。退休日志引用的序号在回收完成前仍被保留，避免重启后新段复用一个还在日志中的旧名字。

全部过期/删除的输入也通过退休日志一次性退出可见段集合。提交校验除文件身份之外还检查输入是否仍然可见，防止尚未物理删除的退休输入被再次提交。

每轮重写使用独立 UUID 临时文件名，外部排序 run 和 merge wave 从该名称派生。准备结果携带临时文件清理守卫，提交锁获取失败、重写失败或输入校验失败都释放本轮产物。

## 锁范围与索引

单分区优化先在目标分区锁内摘下 active writer，seal 的 I/O 在锁外完成。匹配、发现阶段只获取请求分区候选集合的锁，不获取全表 mutation gate。

分区优化完成后使位置索引快照和主键内存缓存失效，由既有查询/约束路径按需刷新；不在优化收尾阶段持表锁重建全表索引。首次后续索引探测可能因此承担刷新成本。全表优化仍保留原有主动重建索引行为。

## 内存与外部归并

重写的内存额度在进程内共享：heavy phase 取得统一 gate 后才取得 CPU/IO permit，且不持 mutation 锁。分区逐个处理，避免分区数倍增内存，以及在 Rayon 分区任务中阻塞等待 permit。写段的列编码及聚簇排序仍可并行。

内存排序以行宽和 footer 字节估值选择入口，解码时按实际分配量继续检查，超过额度转外部排序。外部 run 按实际行数据字节累计，排序后分块输出，不构造第二份完整排序 batch。归并每路固定保留当前行组，根据实际块大小选择 fan-in；输出按行数或字节额度刷新。非聚簇路径的引用缓冲、行组缓存和输出 gather 也分配各自额度。

256 MiB 是重写算法的工作额度，不是进程 RSS 硬限制：文件映射、共享 reader cache、编码器及 footer 元数据另有开销。当前读取 API 的最小解码单位为一个列/行组；单个输入行组超过其额度时返回 `ResourceBusy`，保留原段，而非继续扩大整个分区的分配。

## 统计与错误

各分区仍独立提交。Compactor 保存已提交统计，即使后续分区失败，SQL 入口、后台整理和收盘优化也会按已成功提交的 TTL 删除量修正 catalog，再传播错误。错误不表示前面的分区被回滚。

## 回归测试

`src/storage/core/compactor/audit_test.rs` 覆盖流式漏读、重叠准备、Windows 删除失败与恢复、旧读者跨多轮替换、退休序号保留、TTL 小段清理、部分失败统计、索引表分区锁隔离、真实多轮外部归并以及超预算清理。

原 `external_merge_sort_*` 测试改为直接调用外部归并入口，避免小数据落入内存分支而产生虚假的覆盖。
