# 内存与性能专项审计

## 范围与结论

基线：8041c5a，当前分支 dev。审计方式为核心路径静态检查与现有定向测试；未修改业务源码，未运行业务数据压测。不是全工程无缺陷证明。

需求覆盖清单：
- [x] 内存泄漏：字典解码错误分支与发布订阅元数据生命周期。
- [x] 内存放大：排序输入、合并、排序键、输出及外排归并。
- [x] 性能：外排归并扇入、重复分配与全局互斥。
- [x] 现有保护核查：查询结果保留上限、协议解压输出检查、有界广播。
- [x] 验证与限制：记录构建、定向测试、全库超时及未验证项。

## F1：损坏字符串字典触发永久堆内存泄漏

优先级 P1；代码确认，未做 RSS 复现。

证据：src/storage/codec/column_codec.rs:1462-1471。字典字符串遇到非法 UTF-8 时，将有损转换后的字符串传给 Box::leak 并保存为 &'static str。该分配没有释放路径，后续列、查询或 reader 销毁也不会回收。

触发条件：解码包含非法 UTF-8 字典项的数据。正常写入器校验 UTF-8，因此不能把它描述成每次正常查询必然泄漏，也未证明外部请求可以直接构造此数据。

影响：重复读取同一损坏字典会重复泄漏；泄漏量与非法字典项修复后字符串总字节数及解码次数有关。

建议：对损坏字典返回格式错误，或使用 Cow<str>/拥有型字典保管有损转换字符串；增加损坏字典重复解码与错误返回测试，禁止以泄漏处理损坏数据。

## F2：排序峰值分配没有被输入预算完整覆盖

优先级 P1；代码确认多阶段同时驻留，实际倍率待压测。

证据：src/sql/execution/operators/sort.rs:76-108 的缓存与外排决策，以及 :157-209 的排序物化。排序阶段合并输入列、计算排序键、分配行索引，最后通过 column.take(&rows) 构造输出；输入预算不能等同于该阶段总工作集上限。

影响：宽表、长字符串或复杂排序表达式可能在尚未达到预期查询内存限制时出现显著峰值。不能仅凭源码宣称固定放大若干倍：不同 ColumnArray 的共享、复制与表达式结果大小不同。

建议：对合并、键、索引、输出建立统一内存预留；按峰值而非只按输入大小决定外排；限制单 run 大小，评估间接排序和可分批输出，补充宽字符串与复杂 ORDER BY 的峰值分配测试。

## F3：外排归并没有限制同时打开的 run 数与首批驻留量

优先级 P1；资源增长由代码确认，未做文件句柄/内存压力复现。

证据：src/sql/execution/operators/sort.rs:380-384 遍历全部 spills 并创建全部 SpillCursor；:283 首次加载批次；:287-295 读取各 run 的 row group 并保存批次及键。归并开始前，各 run 的首批与键即可同时驻留。

影响：run 数增加时，归并状态、reader 资源和首批内存随之增长；外排不保证内存始终固定在一个小预算。低预算的大查询尤其应验证。尚未量测实际文件句柄占用，不将句柄耗尽写为已复现事实。

建议：设置有限归并扇入与多轮归并，限制所有 cursor 的总驻留预算，并对大量小 run 添加压力测试。

## F4：主题序号表缺少回收，长期运行可能持续增长

优先级 P2；生命周期代码风险，动态增长未复现。

证据：src/pubsub/mod.rs:202、240 定义并初始化 topic_seqs；:347 和 :382-385 根据 db.table 插入并更新。该字段的源码引用中没有 remove、retain 或 clear 路径。

触发条件：有订阅者时，不断对不同数据库/表主题发布事件，例如长期创建、写入、删除大量不同表；不是同一固定主题每条事件都新建条目。

影响：已消失主题的字符串键和序号可能存活至 PubSubHub 销毁；还会经过同一 Mutex。固定主题集合下不会无限增长，因此应称为条件性元数据滞留，而非每条消息泄漏。

建议：结合表删除、订阅及序号连续性要求设计回收或受限元数据策略，不能盲目清空导致订阅序号语义变化；补充主题 churn 测试。

## F5：外排每行键表示增加分配与比较成本

优先级 P2；代码层面风险，尚未基准证明性能回退。

证据：src/sql/execution/operators/sort.rs:294 为每批调用 evaluate_batch_sort_keys，相关实现 :217-259；外排归并同时保留各 cursor 的键。与列式键比较路径相比，应关注逐行标量键容器与字符串转换的分配成本。

建议：用窄整数键、长字符串键、多列键分别跑基准，记录吞吐、分配次数和峰值；评估列式键或借用视图。未测量前不承诺具体收益。

## 已有保护与避免误报

- src/sql/execution/query/select_exec.rs:762-784 对保留结果调用 query_memory::push_result_batch，不能描述为完全没有查询结果限制。
- src/protocol/compress.rs:37 存在解压输出检查，不将其报告为完全无上限解压。本轮未穷尽所有边界，检查位置与最终输出语义仍可后续专项验证。
- 发布订阅使用有界广播；本轮未发现可证明的 Arc 引用环或正常路径永久泄漏，不因使用 Arc 或缓存就判定泄漏。

## 后续建议顺序

先修复 F1；再给 F2/F3 建立统一内存预算与有限归并扇入；随后处理 F4 生命周期并对 F5 进行性能基准。后续应在隔离环境加入损坏字典、宽字符串排序、大量 run、主题 churn 及连接取消/后台任务关闭的长期测试。本轮没有取得进程 RSS 曲线、分配器统计或生产负载样本，因此不声称已定位所有增长来源或完成全工程性能验收。
