## F6：不完整帧按声明长度提前预留接收容量

优先级 P1；代码确认提前预留，未做网络压力复现。

证据：src/protocol/codec.rs:50-69。在 payload_len 未超单包限制、但当前缓冲不足一帧时，直接 src.reserve(total_len - src.len())。实际正文尚未全部到达就申请声明帧大小的容量。并非长度检查缺失，而是单帧限制不能替代跨连接总预算。

默认配置：src/common/config.rs:12-14 的最大连接数 1024；:27-29 空闲超时 300 秒；:303-309 普通消息上限 64 MiB、bulk 消息上限 128 MiB。上述默认值只说明应重视聚合接收内存，不等同于本轮测得的实际驻留内存，也不保证所有连接可同时走到同一路径。

影响：在大合法帧传输、慢上传或许多连接并发时，可在请求开始执行前积累较大接收容量。执行并发限制不自然等价于接收缓冲预算。BytesMut 容量、虚拟内存提交和 RSS 是不同指标，尚未量测本进程的具体表现。本轮不提供外部触发脚本，也未启动对外服务。

建议：改为受限分块扩容，给接收缓冲设置全局及每连接预算；对正文读取设置总时限/进度约束；大消息考虑流式消费。用隔离的 codec 单元测试验证少量输入不会立即预留整个大帧，再做受控容量统计。

## F7：预编译语句保留最后一次执行参数，缓存只有条数上限

优先级 P1；持有链代码确认，未测量生产内存。

证据：src/sql/execution/prepared.rs:11 默认上限为 4096 条，:20 的 PreparedStatement.params 拥有参数向量；src/net/handler.rs:1009-1025 取出语句、stmt.params = params、执行后直接 insert(stmt)；src/sql/execution/engine/core.rs:376-459 使用 prepared.params 绑定参数，但本段没有在返回前清空参数；src/sql/execution/prepared.rs:104-109 重新入缓存和关闭逻辑。

影响：长生命周期会话的多个语句可以各自保留最后一次执行的大字符串/二进制参数。语句还持有 SQL、AST 和可选计划，单纯限制语句数量不能给会话总字节量提供较小上限。不是每次重复执行同一语句都会累积一份：赋值会释放旧参数；关闭语句、清空缓存或销毁会话可以释放。

建议：先确认协议是否允许后续执行复用已绑定参数；若每次 EXECUTE 都携带完整参数，则执行后及时清空 params。为 SQL/AST/计划/参数建立会话级字节预算，增加大参数执行后缓存驻留量测试，避免仅测条数限制。

## F8：排序内部长计算缺少取消安全点，断连后资源可能延迟释放

优先级 P2；代码层面确认检查位置不足，实际延迟待压测。

证据：src/sql/execution/operators/sort.rs 的输入拉取循环包含 query_cancel::check，但 :155-209 的合并、排序键、sort_by 及输出 take 路径没有同等粒度检查；:397-461 的归并输出段同样需要结合批次大小评估响应延迟。src/net/server.rs:381-413 表明阻塞 worker 超过断连等待后由 detached reaper 等待其完成，不能靠 abort 强制结束。

影响：取消标志已经设置不等于当前排序立即停止。大排序可能在下个安全点前继续耗 CPU 并持有内存、handler 和执行资源；这是条件性延迟释放，不是已经证明永久泄漏。已有取消测试通过，不代表覆盖取消恰好发生在 sort_by 中的情况。

建议：在阶段边界、合并/键求值/输出构造的分块循环加入取消检查；单个不可中断排序段限制 run 大小或改用可分段算法。增加进入排序内部后触发取消的同步测试，分别记录返回延迟、后台 worker 结束时间和资源回落。
