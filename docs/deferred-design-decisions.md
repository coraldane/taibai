# 有意不做"顺手修"的五项:需要产品/架构决策

以下五项不是 bug,而是会改变执行模型或产品语义的架构工作。每项给出问题、
可选方案与建议,供立项决策。在此之前保持现状是安全的(各有明确的文档化代价)。

## 1. 查询输入侧全量物化 / 聚合不流式

**现状**:`is_streamable`(scan/cursor.rs)把 count/聚合/排序/join 全部排除在
流式扫描之外,`execute_scan` 无界收集全部输入批,内存限额在物化完成后才检查
(query.rs);聚合/排序这类最受益于流式的形状反而全部物化。

**方案选项**:
- A. 火山模型改造:为 Aggregate/Sort/TopN 提供 pull-based 输入接口,
  聚合改增量(分组哈希表本身就是增量的,缺的是流式输入);
  Sort/TopN 本就有 spill,只差流式喂数。
- B. 保持物化,但把"输入侧限额"从"事后报错"改为"边收集边检查"
  (LimitedBatchSink 加字节数上限,超限即报错)——半天工作量,
  把 OOM 变成干净错误,但不减内存峰值。
- **建议**:先做 B(立即消除 OOM 风险),A 作为独立执行器项目立项。

## 2. 压缩策略(纯 major → 分层/脏度过滤)

**现状**:任一分区 ≥2 段即整分区重写(compactor.rs),唯一跳过条件是
"无排序键且单段干净";表级 30%/8192 门槛控制触发频率,但单次成本与脏字节数
无关;有活跃分区时连活跃段并入(`compact_table_for_fragmentation`)。

**方案选项**:
- A. 脏度过滤:只重写"脏"段,干净段原样保留(需要段级替换协议支持
  部分替换——现有 replace_segments_with_tmp 已支持段集合,可行)。
  代价:碎片整理目标(减少段数)与脏度过滤冲突,需要两个独立通道。
- B. Size-tiered:按段大小分桶,同桶合并——改动选择器即可,但与
  CLUSTER BY 的全局有序性冲突(cluster 表必须全分区归并才能保序)。
- **建议**:非 cluster 表走 A(脏段单独重写),cluster 表维持 major;
  触发阈值保持。属于独立项目,需要先明确"碎片整理"的优先级。

## 3. 宽度型 ALTER 收敛期:并发 DML 排队 vs 报错

**现状**:DDL 收敛窗口内并发 DML 自旋到 `mutation_lock_timeout_secs` 后收到
ResourceBusy 硬错误,不排队。

**方案选项**:
- A. 公平排队:acquire_partition_mutation_lock 从 try_lock+backoff 改为
  condvar/公平锁——消除报错,但 DDL 卡住时 DML 会无声堆积(内存压力
  转移到等待队列),且改锁原语风险高。
- B. 客户端重试语义:把 ResourceBusy 映射为协议层"请重试"错误码,
  客户端驱动自动退避重试——不动内核,改 handler + 客户端。
- **建议**:B。数据库内核报"忙碌请重试"是主流做法(PostgreSQL 锁等待
  是显式会话语义,与这里单语句模型不同)。

## 4. 元数据聚合的混合执行(单段漂移不整体退化)

**现状**:aggregate_meta.rs 遇到任一 schema 漂移段即整体放弃元数据快路径,
退化为全表流式扫描(正确但慢;一次 ALTER 后、压缩重写漂移段之前持续如此)。

**方案选项**:
- A. 混合执行器:干净段走 footer/col_sums 折叠,漂移段流式读入同一聚合。
  需要把元数据快路径从"一次算完"改成可组合的聚合器接口,中等工作量。
- B. 漂移段标记:ALTER 时给漂移段排一次"元数据回填"任务(后台把
  col_sums 写进 footer sidecar),快路径恢复——不需要新执行器,但
  需要 sidecar 扩展与后台任务调度。
- **建议**:B 便宜且治本;A 是通用能力,若流式执行(第 1 项)立项则顺路。

## 5. 冷段 UPDATE 整段重写 → 增量段格式

**现状**:冷段单行 UPDATE = 整段重写(已流式化,峰值一行组)+ 每索引
全表扫描重建;8GB 段更新 1 行 ≈ 16GB IO。这是当前最大的写放大项。

**方案选项**:
- A. 行组级替换:段格式增加"行组替换表"(类似 delete bitmap 的间接层),
  UPDATE 只重写受影响行组 + 追加替换表——格式版本 + 迁移工具 +
  读路径全部要动,是最大的单项工程。
- B. UPDATE 路由热存:冷段 UPDATE 改为"段内标记删除 + 行进 memtable",
  依赖压缩异步回收——语义上已是 DELETE+INSERT 的特例,改动集中在
  dml_update 的段腿;代价是 cluster 有序性被打破(新行在尾部)。
- **建议**:如果 UPDATE 多为热点行,先做 B(小改);A 需要专门 RFC。
