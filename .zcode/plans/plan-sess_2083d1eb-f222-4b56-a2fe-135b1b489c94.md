# 存储压缩率与 .meta 膨胀优化方案

## 目标
在不影响查询效率、保证数据绝对正确的前提下,降低 .dat 体积和 .meta 膨胀。用户已确认:无 SET 索引、压缩级别统一 3、极致压缩全做。

## 核心原则(贯穿所有改动)
- **读侧零改动**:所有编码格式改动都复用 reader 已支持的 MAGIC 自描述机制,老数据/新数据共存兼容。
- **裁剪保守兜底**:value_set 关闭后,裁剪函数 None 分支 = 不裁剪 = 读取后逐行过滤,**绝不丢数据**。
- **zstd 解压与级别无关**:统一压缩级别 3 对存量/增量数据 100% 兼容。

---

## 改动一:压缩级别统一为 3(1 个文件,最安全)

**文件**:`src/storage/segment_manager/config.rs:35`

将 `bulk_compression_level()` 默认值从 `1` 改为 `3`:
```rust
.unwrap_or(3)   // 原 unwrap_or(1)
```
- 覆盖路径 A 三处调用点:`active_writer.rs:186`、`segment_manager.rs:1086`、`segment_manager.rs:1467`。
- 路径 B(`writer.rs:158`)已固定 3,无需改。
- WAL(`wal_helper.rs:131`)独立链路,保持不动。
- 查询效率:解压速度与压缩级别基本无关,符合要求。

---

## 改动二:关闭 value_set 构建(.meta 瘦身核心,最大收益)

用户确认无 SET 索引,value_set 写了也永不被读取。保留 footer magic 占位以保证二进制格式兼容(reader 靠 magic 定位后续 delete_bitmap,不能删 magic)。

**改动点(3 处构建逻辑全部置 None)**:

1. `src/storage/segment/writer.rs:46`
   - `vec![Some(HashSet::new()); num_columns]` → `vec![None; num_columns]`
   - 这样 `write_batch` 路径(`:146-152`)不再插入任何值,value_set 始终 None。

2. `src/storage/segment_manager/active_writer.rs` 的 `compute_value_sets_from_batch`(约 `:414-444`)
   - 直接返回 `vec![None; self.schema.num_columns()]`,不再构建。

3. `src/storage/segment_manager/helpers.rs:347-375` 的 `compute_value_sets_from_bulk_columns`
   - 直接返回 `vec![None; num_columns]`。

4. `src/storage/segment_manager/active_writer.rs:229`(flush_buffer 调用处)
   - `value_sets: compute_value_sets_from_batch(...)` 调用保留(返回 None 向量),无需改动调用点;或直接内联为 `vec![None; num_columns]`。

**footer 序列化不变**:`writer.rs:388-399` 仍写 magic + 每列 `has_set=0`,reader `footer.rs:146-165` 正常解析为全 None。`reserved_section_offset`/`skip_value_set_extension`(`footer.rs:283-308`)正常工作,delete_bitmap 重写不受影响。

**正确性**:已核验 `row_group.rs:36,48` 为 `if let Some(Some(values))` 保守模式,None 时跳过裁剪,rowgroup 照常读出 + `row_filter::apply_predicates` 逐行精确过滤。零数据风险。

**预期收益**:.meta 从 1.7G/151M 降到 MB 级(剩余主要是 zone_map + size 数组 + journal)。

---

## 改动三:sidecar .meta compact 阈值调优(防 journal 累积)

分区表共享 .meta(`p20260709.meta` 服务该分区所有 segment),journal 累积是 .meta 膨胀的次因。

**文件**:`src/storage/segment_manager/config.rs:8-9`
```rust
pub(super) const SIDECAR_COMPACT_MIN_RECORDS: usize = 256;  // → 调小,如 32
pub(super) const SIDECAR_COMPACT_MIN_BYTES: u64 = 4 * 1024 * 1024;  // → 调小,如 1MB
```
让 compact 更积极,把累积的 journal delta 更快合并成单条 FULL_SNAPSHOT。配合改动二(value_set 关闭后单条 snapshot 本身已极小),.meta 可稳定在低水位。

**正确性**:compact 是 atomic_replace(`meta.rs:280`),无数据风险。

---

## 改动四:路径 A 列编码 adaptive 化(压缩率提升 30-50%)

路径 A 三处编码入口目前是裸字节 memcpy,时间戳/数值列没有 delta/rle。改造为复用 `column_codec.rs` 的 adaptive payload + MAGIC 格式,reader 零改动自动识别。

**编码逻辑封装**:在 `src/storage/column_encoding.rs` 新增一个函数 `encode_direct_column_adaptive(col, start, len)`,内部:
- 对 `ColumnArray` 的数值/时间戳类型,调用 `column_codec.rs` 里已有的 `choose_numeric_encoding`(delta/rle 选择器,`:143`)生成 payload;
- 若 adaptive 收益 < plain,回退裸字节;
- 输出格式:`0u32`(空 bitmap 头,reader 解读为"全非空")+ 可选 `COLUMN_ENCODING_MAGIC` + encoding_type + payload,与 reader `decode_column`(`column_codec.rs:295`)完全兼容。

**改造调用点(3 处)**:

1. `active_writer.rs:195` `flush_buffer`(SQL INSERT 路径)
   - `encode_column_direct_range(col, 0, rows_to_flush)` → `encode_direct_column_adaptive(col, 0, rows_to_flush)`

2. `segment_manager.rs:1082-1084` `bulk_insert_payload` 直连路径
   - 把 `0u32 + col.data` 裸拷贝替换为 adaptive 编码(基于 `DirectBulkColumn` 的 data_type 解析裸字节为数值切片,再走 delta/rle)。

3. `segment_manager.rs:1471-1473` `compress_direct_bulk_columns`
   - 同上。

**兼容性保证**:
- reader `decode_column`(`column_codec.rs:295-308`)读 `u32 bitmap_len` 后,检查 `remaining.starts_with(b"MXE1")`,匹配则走 `decode_adaptive_column` 按 EncodingType 分发。**新增的 MAGIC 数据老 reader 直接可读,老数据(无 MAGIC)也照常 plain 解码**。
- 谓词下推路径 `predicate_scan.rs:24,50` 同样检查 MAGIC,自适应。
- delta 编码只在数值单调非递减时启用(`choose_numeric_encoding:155`),时间戳列天然满足,收益最大;非单调列回退 plain,零风险。

**关键约束处理**:
- `choose_numeric_encoding` 要求 `values.len() >= 128`(`:144`),rowgroup 50万行远超阈值。
- direct bulk 路径的 `DirectBulkColumn.data` 需按 data_type 重新解释为数值切片(定长类型已是小端序布局,可直接 `from_raw_parts`)。变长类型(VarChar)走 dictionary adaptive(复用 `encode_varchar_dictionary_adaptive`)。

## 改动五(可选,低风险):bloom filter 参数调优

active 段不建 bloom(确认 `active_writer.rs:115,228` 全 None),只在 compact 后对 cluster key 列建。当前固定 8192 items(`bloomfilter.rs:8`)。若后续需要,可让 bloom 按实际 rowgroup 行数分配,但对当前问题(stock_tick 的 .meta 主因是 value_set)非必要。**本次默认不动**,除非用户要求。

---

## 不做的事(避免风险)
- 不动 rowgroup 行数(50万):调大会粗化裁剪粒度 + 内存峰值 ×4,与"不影响查询效率"冲突。encoding 改造后单 rowgroup 压缩率已大幅提升,无需靠调大 rowgroup。
- 不动 WAL 压缩(独立链路)。
- 不改 reader 任何代码。
- 不删 footer 里的 value_set magic(否则破坏 delete_bitmap 重写定位)。
